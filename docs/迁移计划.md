## 目标定位

基于参考项目的 apps/backend/rest-api 提炼独立 Express API 服务脚手架。

这个脚手架用于服务通用 Web App，不是 CMS 后端，不是 RBAC 管理后台，也不是 monorepo 子包。

本项目只保留参考项目后端的技术栈、分层风格和通用基础能力，不保留参考项目的 monorepo 仓库形态、前端编排方式、workspace 依赖和具体 CMS 业务。

保留参考项目后端的技术栈和代码组织方式：

- Express
- TypeScript
- pnpm
- Sequelize / MySQL
- Redis
- JWT
- Zod
- Swagger
- Multer / file upload
- Docker

删除 monorepo、前端、RBAC、CMS 业务相关内容。

## 核心迁移原则

### 保留后端应用结构，不保留旧仓库结构

迁移时以参考项目的后端应用 `apps/backend/rest-api` 为母版，将它提升为当前独立后端仓库的根目录。

保留旧后端的应用分层：

- routes 只负责路径和中间件编排
- controllers 只负责 HTTP 入参/响应适配
- services 负责业务规则和 DB / Redis 调用
- models 负责 Sequelize 模型定义和关联
- schema 负责 Zod 校验
- middlewares 负责通用横切能力
- utils / types 负责通用工具和类型

不保留旧项目的仓库组织：

- 不保留 apps/backend/rest-api 包裹目录
- 不保留 pnpm-workspace.yaml
- 不保留 packages/shared、request-core、js-bridge、web-monitor
- 不保留前端应用和前端 Docker 编排
- 不保留根目录跨包 filter 脚本

### 技术栈严格对齐旧后端

独立仓库继续使用参考项目后端已有技术栈，不重新设计框架，不引入新的无关基础设施。

从 monorepo 迁出后，需要将旧项目中 `catalog:` 和 `workspace:*` 形式的依赖落到独立仓库可直接安装的真实依赖版本。

`@express-vue3-monorepo/shared` 不再作为依赖保留。后端实际需要的常量、类型或工具代码，复制到当前后端仓库内部，并保持逻辑与参考项目一致。

### 先裁剪业务，再修正耦合

RBAC、CMS、admin、post、comment、category 等内容属于业务裁剪。

env、swagger、uploads、Docker、scripts 中依赖 monorepo 根目录的逻辑属于仓库形态耦合修正。

这两类问题要分开处理，不要为了删除业务模块而改动通用基础设施的设计风格。

## 依赖处理

技术栈、依赖版本、运行方式严格参考原项目后端。

原项目中依赖 @express-vue3-monorepo/shared 的地方，不再保留 workspace shared 依赖。只复制后端实际需要的类型、常量或工具代码到当前后端仓库中，并保持代码逻辑与参考项目一致。

例如大文件上传 schema 中使用的 `LARGE_UPLOAD_MAX_FILE_BYTES`，应迁移到当前仓库内部的常量文件，而不是继续依赖 shared 包。

原项目 package.json 中的 `catalog:` 依赖版本，需要参考 monorepo 根目录 pnpm catalog 或 lockfile，迁移为独立仓库 package.json 中可直接安装的版本号。

不要为了替代 shared 依赖而新增无关抽象或额外能力。

### 模块去留与依赖增删绑定

模块的保留/删除必须与 package.json 依赖同步，避免留下无用依赖或漏装必需依赖：

- 保留 upload → 必须保留 `multer` 与 `@types/multer`。
- 删除 CMS 内容审核（content-safety）→ 同步删除 `sanitize-html` 与 `@types/sanitize-html`。
- 大文件上传 schema 使用的 `LARGE_UPLOAD_MAX_FILE_BYTES`（参考项目在 `packages/shared/src/constants/largeUpload.ts`，值为 `1024 * 1024 * 1024`）迁移到当前仓库内部常量文件，不再依赖 shared。

其余依赖严格对齐参考项目后端 package.json（express、sequelize、mysql2、redis、jsonwebtoken、bcrypt、zod、winston、helmet、cors、compression、express-rate-limit、js-yaml、swagger-ui-express、multer、dotenv、cross-env 等），并把 `catalog:` / `workspace:*` 落成可安装的真实版本。

原项目中和 monorepo 根目录相关的逻辑需要适配独立仓库。例如 env.ts 不再使用 findMonorepoRoot 查找 monorepo 根目录，而是基于当前独立仓库根目录读取 .env.* 文件。

以下文件或逻辑需要重点检查 monorepo 路径假设，并按结论处理：

- env.ts：删除 `findMonorepoRoot` 调用，改为基于当前仓库根目录的 `projectRoot` 读取 `.env.*`。
- monorepoRoot.ts：删除该文件（env.ts 不再依赖它）。
- projectRoot.ts：保留，改为解析当前独立仓库根目录。
- swagger.ts：openapi 文档路径基于当前仓库根目录，不依赖 monorepo 根。
- upload.config.ts：`uploadsRoot` 基于当前仓库 `projectRoot` 下的 `uploads/`。
- large-upload.service.ts：会话/哈希索引/完成标记等 `.data/` 目录基于当前仓库 `projectRoot`。
- Dockerfile / docker compose：build context 为当前仓库根，不再使用 pnpm workspace filter，不再 COPY 前端或 packages。
- scripts 中的数据库、种子和测试脚本：删除 monorepo/CMS 相关脚本，仅保留通用脚本（见「scripts 迁移范围」）。

### scripts 迁移范围

只保留独立后端运行所需的通用脚本，其余（CMS 种子、synthetic-it 系列、RBAC 引导、monorepo 探测/合并 dotenv 等）一律删除。

保留：

- `scripts/reset-db.ts`（数据库重建，去掉 CMS 种子调用与 monorepo 路径假设）
- `scripts/test-env.ts`（环境自检，去掉 monorepo 路径假设）

删除（示例，非通用能力）：

- `find-monorepo-root.ts`、`synthetic-it-merge-monorepo-dotenv.ts`（monorepo 假设）
- `ensure-super-admin.ts`（RBAC）
- `it-seed-categories.ts`、`it-category-seed.*`、`synthetic-it-*`、`dedupe-mysql-redundant-indexes.ts` 等（CMS 种子/集成脚本）

package.json 中对应删除脚本的 `scripts` 命令也要同步移除，只保留 `db:drop-create`（reset-db）与 `test:env` 等通用命令。

## Auth/User 业务边界

auth 和 user 相关业务都保留。

包括但不限于：

- 注册
- 登录
- 退出登录
- 当前用户信息
- 用户资料
- JWT 登录凭证
- Redis JWT blacklist 退出登录逻辑
- auth middleware
- optional auth middleware
- JWT 校验逻辑

迁移时按参考项目已有实现处理，不重新设计接口和业务逻辑。

由于本脚手架不需要 RBAC，auth/user 中和 RBAC 绑定的内容需要裁剪：

- User 模型不保留 roleId
- JWT payload 不保留 roleId / roleSlug
- getMe 返回值不保留 roleId / roleSlug / permissions
- 注册逻辑不再创建或绑定默认 Role
- 登录逻辑不再查询 Role
- 删除 rbac.service、rbac-bootstrap.service、permission-codes 等 RBAC 依赖

RBAC 裁剪不能只删除 rbac 目录或 service，需要同步修正所有引用链路：

- User 模型字段和关联
- db.ts 中的模型初始化和关联
- models/index.ts 导出
- jwt-user 类型
- auth.middleware / optionalAuth.middleware
- auth-token / jwt 校验服务中的 payload 类型
- auth.service 注册、登录、登出逻辑
- user.service / getMe 返回值
- OpenAPI 文档
- 相关测试

参考项目没有 refresh token 路由，不要新增 refresh token / session 体系，除非后续另行明确要求。

保留 Web App 通用认证能力即可：

- register
- login
- logout
- me
- me/profile

## 文件上传边界

文件上传属于 Web App API 的基础能力，需要保留。

保留参考项目中的通用上传能力：

- multer 本地磁盘上传配置
- /uploads 静态资源访问
- 用户头像上传
- 通用图片上传
- 分片大文件上传能力

上传实现仍按参考项目方式迁移，但需要去掉 CMS 语义：

- 不再使用 posts 作为通用上传目录语义
- 改为 common、images 或 files 等通用目录命名
- 保留 profiles 作为用户头像/资料图片目录
- 上传接口不绑定 post/comment/category 等 CMS 业务

上传模块需要保留的相关内容包括：

- src/config/upload.config.ts
- src/config/large-upload.multer.ts
- src/controllers/upload.controller.ts
- src/controllers/large-upload.controller.ts
- src/routes/upload.routes.ts
- src/schema/large-upload.schema.ts
- src/services/large-upload.service.ts

去 CMS 语义时的具体改动：将 upload.config.ts 中 `postUploadDiskSegment = "posts"` 改为通用命名（如 `commonUploadDiskSegment = "common"`），对应中间件与落盘目录由 `uploads/posts/...` 改为 `uploads/common/...`；`profiles`（头像/资料图）保留不变；大文件成品目录 `uploads/large/...` 与临时分片目录 `uploads/chunks-temp/...` 保持不变。app.ts 中 upload 路由与 `/uploads` 静态资源（`express.static(uploadsRoot)`）必须迁移。

如果某些上传逻辑只服务帖子富文本、CMS 内容生产或前端编辑器，需要裁剪为通用文件上传逻辑。

注意：这里删除的是 CMS 内容相关模型和业务依赖，不是删除上传基础能力。参考项目中上传主要是基于磁盘、Multer、静态资源和大文件分片服务实现，独立脚手架应保留这些通用能力，但不要引入 post/comment/category 语义。

## 建议实施顺序

1. 迁移 package.json、tsconfig、vitest、nodemon、基础 scripts，先保证独立仓库能安装依赖。

9. 最后清理残留的 monorepo、frontend、RBAC、CMS 引用，并补齐测试和文档。
